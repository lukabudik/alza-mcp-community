# Changelog

All notable changes to this project will be documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- `ALZA_TOOLSETS`: toolsets to enable at startup (`basket_and_checkout,orders_and_payments` or `all`) for MCP clients that never re-fetch the tool list after `set_toolset` fires `notifications/tools/list_changed` (reported 2026-10-11 for Grok Bot, which kept showing only the 13 default tools). `list_toolsets` and `set_toolset` now mention it. An unknown id is a startup error.
- `scripts/local-canary.sh` and `docs/live-canary-local.md`: run the live canary from a home or office machine (where Cloudflare lets the checks through) and report like the workflow: open or comment on one `canary` issue on failure, comment and close it on recovery, file nothing when Cloudflare challenges the machine. It works in its own clone and is anonymous. Schedule it with a systemd user timer or cron.

### Fixed
- The API layer no longer hard-codes Czech for other storefronts. With `ALZA_BASE_URL=https://www.alza.sk`, `autocomplete` returned Czech suggestions (or a Cloudflare 403), `get_product_reviews` listed Czech reviews, and the navigation, chatbot, order, claim, subscription, account and watchdog routes all sent `country=CZ` and `Accept-Language: cs-CZ`. `MobileApi` now takes the storefront locale (`locale` option, wired from `ALZA_BASE_URL`; inferred from a storefront `baseUrl` otherwise; CZ by default) and uses its country and language on every route, in AppAction requests, and as the default OAuth `countryCode`/`culture` (`ALZA_COUNTRY`/`ALZA_CULTURE` still override). The hosts stay the same: `webapi.alza.sk` and `chatbotapi.alza.sk` do not exist, and the shared `.cz` hosts answer `country=SK` with alza.sk data (live-verified 2026-10-12: whisper `eshopUrl=https://www.alza.sk/`, Slovak reviews matching the SK review count, `chat_navigation`). The chatbot tools' `country` argument now defaults to the storefront. The account writes (2FA, phone, email, account deletion, watchdog create/delete, basket unlock) still send `country=CZ` on every storefront: they are live-verified on CZ only. Tests: `test/mobile-api-locale.test.ts`, including one that sets `ALZA_BASE_URL` and checks the country `autocomplete` sends.
- Streamable HTTP transport now enforces the 4 MB body size limit on existing sessions as well as during initialization: `readJsonBody()` now meters and validates incoming POST request bodies carrying a `Mcp-Session-Id` header, returning HTTP 413 `request body too large` if exceeded, rather than forwarding unbounded streams to the SDK transport.
- Follow-up to the body limit on existing HTTP sessions: a session POST that is not `application/json` is no longer parsed here, so it gets the SDK's 415 again instead of a 400. A session POST with more than one `Content-Type` header is refused with 400: Node keeps the first value and the SDK joins them, so `text/plain` + `application/json` would otherwise skip the limit here and be parsed by the SDK without one. Tests now also cover a chunked oversized body, the 415 and the repeated header.
- Catalog tools no longer report an empty result when Alza's Cloudflare bot protection blocks the headless browser (reported 2026-10-11: `search_products`, `get_product` and `list_categories` all returned nothing while every navigation got HTTP 403 with `cf-mitigated: challenge`). `search_products`, `get_product`, `compare_products`, `list_categories`, `list_category_filters`, `get_product_reviews` and the PC builder now fail with a Cloudflare-challenge error that names the status and the ways out (`ALZA_PROXY_URL`, `ALZA_CDP_URL`, retry), and any other 403/429/5xx on a catalog page is an upstream error instead of "0 results". 404 still means not found / no results.
- Follow-up to the visible-availability fix (Refs #99): the page's availability line is a client-rendered component that is often still empty at `load`, which silently fell back to JSON-LD `InStock` for on-order items. `get_product` / `compare_products` now wait up to 5 s for it, read only the status span (not the delivery promo text that used to be appended to `availabilityText`), and set the new `jsonLdAvailability` field (also shown in the text output) when the structured data disagrees with the visible line. Live-verified 2026-10-08 on YUBIK002a10 (on order) and YUBIK002a5 (in stock). Search cards still only know whether a purchase CTA exists.
- The server no longer accepts requests before the MCP `initialize` handshake ([#80](https://github.com/lukabudik/alza-mcp-community/issues/80)). The SDK allows them by default, so every transport is now wrapped in `InitializeGuardTransport` (`src/infra/initialize-guard.ts`, used for stdio and for each Streamable HTTP session): until the `initialize` request has been answered successfully, any request other than `initialize` and `ping` gets a JSON-RPC `-32002` ("Server not initialized") error and never reaches a handler, and notifications are ignored. Nothing changes after the handshake; stdio still answers malformed JSON with `-32700`. HTTP already refused sessionless requests, so the guard there only closes the window between session creation and the initialize response. Tests: raw JSON-RPC over an in-memory pair, a stdio child process, and HTTP.
- `search_products` no longer rejects a blank query for facet or range searches (category + `producer_ids`, `filters` or `ranges`), which go through the category-browse path that ignores the query. The QA blank-query check had broken `scripts/validate-api.ts`' "category + producer" check; the canary now passes it again.
- `get_product` / `compare_products` / PC-builder stock: availability now comes from the visible `.av-container` line on the product page instead of JSON-LD alone. Live-verified 2026-10-08: YUBIK002a10 had JSON-LD `InStock` while the page said "Na objednávku – termín upřesníme". The JSON-LD value remains the fallback, and `inStockFrom` understands the Czech texts (`Skladem…` true; `Na objednávku`, `Není skladem`, … false).

### Changed
- SECURITY.md no longer says private vulnerability reporting is available: it may not be enabled on the repository, so the documented interim channel is a minimal public issue (no technical details) asking for a private contact channel.
- GitHub repository links in the changelog now point to `lukabudik/alza-mcp-community`, the repository's new name (the old URLs still redirect). The repository URL fields in `package.json`, `server.json` and `mcpb/manifest.json`, the `report_issue` repo and `gh` commands, and the docs already used the new name since 0.6.0. The npm trusted-publisher entry must name `lukabudik/alza-mcp-community`.

## [0.6.0] — 2026-10-07

## [0.5.0] — 2026-10-07

Security hardening of the account and checkout path, a QA pass over the whole server (about 60 findings fixed), link attribution, `report_issue`, proxy support and `--setup-cf`.

**Behaviour changes to know about:**
- Confirmation tokens are single-use, bound to the action and payload, expire after a few minutes, and a failed attempt spends the token (prepare a new one to retry).
- Product, category and suggestion links returned by the catalog tools carry `utm_source=alza-mcp-community&utm_medium=mcp`.
- `search_products` accepts `page` 1–50 and one `producer_ids` value; unknown category ids return an error.
- Tools marked read-only no longer run GET-based changes; a token for one AppAction tool no longer authorises other routes.

### Added
- `alza-mcp --setup-cf` ([#80](https://github.com/lukabudik/alza-mcp-community/issues/80)): a cross-platform, Node-only command that creates the optional `.venv-cf` (finds `py -3`/`python3`/`python`, `python -m venv`, installs `curl_cffi>=0.16,<0.17`, verifies the import, exits 0/1; idempotent; removes a half-built venv; honours `ALZA_MCP_SKIP_VENV=1`) for `.mcpb`, `--ignore-scripts` and Windows installs where the bash script cannot run. The venv lives in the package copy that runs the command, so the `.mcpb` bundle needs `ALZA_CF_PYTHON` pointed at the printed interpreter. Nothing is installed automatically; when the sidecar is unavailable the server logs one info-level hint pointing to `npx -y alza-mcp --setup-cf`. Unit-tested with mocked processes, including Windows paths; still not run on a real Windows machine.
- Alza storefront links returned by the catalog tools (`search_products`, `get_product`, `compare_products`, `recommend_alternatives`, `get_deals`, `autocomplete`, `list_categories`, `pc_build_check`, `pc_build_suggest`, `watchdog_list` and the `alza://product/{code}` resource) now carry `utm_source=alza-mcp-community&utm_medium=mcp`, at Alza's request, so Alza can attribute visits from the MCP. The parameters are added at output time on copies, so cached and internally navigated URLs stay untagged. Only `www.alza.*` storefront hosts are tagged; OAuth, API, PDF, image and payment URLs and the account/checkout passthrough tools are not. Live-checked 2026-10-07: tagged search, detail and autocomplete links open the right product page (HTTP 200).
- `report_issue`, an always-available tool that drafts a GitHub issue for this repository when a tool fails unexpectedly, returns clearly wrong data, or breaks because Alza changed something. It returns a redacted Markdown draft (version, Node, platform, storefront, transport, this session's last 5 tool errors), a `gh issue list` duplicate search, a ready-to-run `gh issue create` command, and a prefilled new-issue link. It files nothing itself; the agent asks the user first. The server instructions mention it, and unexpected tool errors (not invalid arguments or unknown products) end with a hint pointing to it. Credentials, OAuth redirect parameters, JWTs, e-mails, phone numbers, account ids in API paths, long opaque tokens and home-directory paths are redacted.
- `ALZA_PROXY_URL` now works. It was mentioned in the Cloudflare error message and the bug template but nothing read it. An HTTP(S) or SOCKS5 proxy URL, with optional `user:pass@`, routes the managed Chromium (Playwright `proxy`) and the `curl_cffi` sidecar (`Session(proxy=…)`) through it. Verified 2026-10-07 against a local authenticating proxy: a live `search_products` and a sidecar request both went through it with credentials. The live canary passes an optional `ALZA_PROXY_URL` repository secret, because GitHub-hosted runner IPs are challenged whatever the client (see `docs/gap-analysis.md`).

### Changed
- **`prepare_mutation` now requires `payload` and binds the token to it** ([#79](https://github.com/lukabudik/alza-mcp-community/issues/79)). Pass exactly the arguments of the mutation call except `confirmation_token` (for `mutate_list`, its `payload`); the token is bound to the action plus a SHA-256 of the canonical payload (sorted keys, the tool's schema defaults filled in, so omitting e.g. `cancel_order`'s `reason` is fine). A call with different arguments is refused, sends nothing and spends the token. Tokens, including the `checkout_preview` token, expire 5 minutes after issue (`expiresAt` in the result), and each action has its own pending token, so preparing `address_delete` no longer invalidates a pending `watchdog_delete` token. Callers that prepared tokens without a payload must add one.
- **Credential and identity mutations check `user_id` against the signed-in account** ([#79](https://github.com/lukabudik/alza-mcp-community/issues/79)). `change_password`, `email_change`, `phone_change`, `two_factor_set` and `delete_account` read `user_data` right before sending and refuse a different id; if the signed-in user id cannot be read (anonymous `-1`, missing, or the read fails) they refuse and send nothing. Other user-id routes (`order`, `order_search`, `order_archive`, `complaint_claims`, `subscription_overview`, `gdpr_info`, `gdpr_export`, `watchdog_*`, and the user-id `mobile_read` operations) refuse an id that differs from the one `profile`/`user_data` last reported; a new `auth_exchange` forgets it.
- Docs: `docs/mobile-endpoint-coverage.md` now has matrix rows for the tools that lacked one (`list_categories` C21, `list_category_filters` C22, `compare_products` C23, `pc_build_check` C24, and the local-only `account_status`, `prepare_mutation`, `list_toolsets`, `set_toolset`, `report_issue` in a new section 14). Every `live-verified` row carries a date and evidence link; 12 rows whose 2026-09-08 read-journey results were never archived (C1, C10, C11, A1, A6, P1, R3, B10, D3, D4, O7, OR4) are relabeled `source-confirmed` until re-run ([#80](https://github.com/lukabudik/alza-mcp-community/issues/80)). `test/docs-coverage.test.ts` fails when a registered tool has no row, a row id repeats, a status is outside the four allowed labels, or a `live-verified` row has no date.

### Fixed
- `pc_build_check` no longer shows a Discontinued / unavailable part as price `0` with an empty currency ([#78](https://github.com/lukabudik/alza-mcp-community/issues/78)): the price is left unset (`?`), the currency falls back to CZK, the part is listed in `unpriced`, and the report sets `totalIncomplete: true`, prints "excludes N unpriced part(s)" next to the total and adds a note.
- `pc_build_check` role sanity ([#78](https://github.com/lukabudik/alza-mcp-community/issues/78)): a laptop, prebuilt PC or monitor (display / operating-system spec rows) is no longer detected as RAM and is refused even with a forced `role`; a forced `role` that contradicts the part's spec table (a Ryzen forced as `gpu`) is refused, and one that only contradicts the name adds a note. An incomplete build (missing cpu, motherboard, ram, psu or case) now gets the new overall verdict `no_conflicts_found` instead of `compatible`, with `missingRoles` listed in the result and the Markdown header.
- `pc_build_suggest` backtracking ([#78](https://github.com/lukabudik/alza-mcp-community/issues/78)): when a later role (PSU, case, cooler, storage) is left empty because the earlier picks took the budget, the selection retries with cheaper choices for the GPU and CPU (bounded to 20 deterministic combinations, `backtrackCaps`), keeping a retry only if it yields a complete build within the budget; otherwise the original result and a "Backtracking: ... none completes the build" note stay. Budget cap and compatibility rules are unchanged. Live-checked 2026-10-07 (anonymous, budget 40000, `max_detail_fetches` 6): complete 8-role build, 39914 CZK, no retry needed.
- `pc_build_suggest` part quality ([#78](https://github.com/lukabudik/alza-mcp-community/issues/78)): the budget is a hard limit (a card above the money left, minus half of the later roles' allocations, is never picked; the role stays empty with a "cannot fit the budget" note); a PSU below the recommended wattage is skipped instead of kept as a warn fallback; PSU wattage is also read from model numbers such as `RM750x`/`CX650M` for the name pre-filter, and the last detail fetch is kept for the PSU; RAM kits are recognised by a broader name pattern (`2x16GB`, `Dual Channel`), and a fetched single-module candidate is only kept if no kit turns up.
- Catalog low-severity fixes from the 2026-10-07 QA run ([#78](https://github.com/lukabudik/alza-mcp-community/issues/78)):
  - `search_products`: `min_price > max_price` and a blank/whitespace `query` are rejected up front; a price bound now sweeps up to 3 result pages like the price/rating sorts (it applied to one ~24-card page, so `min_price` on "myš" returned 3 of hundreds); `pageSize` is the real cards-per-page instead of echoing `limit`; new `hasMore`/`nextPage` say whether more pages exist; the card parser reads ratings of products with 1000+ reviews (`4,8 4 923×` broke the old pattern, so rated cable cards showed no rating); and Alza's own "nenašel/nenašiel" no-results page is recognised at once, so a typo query no longer waits ~35 s for a grid that never comes.
  - `get_product`, `alza://product/{code}` and `compare_products` report the real numeric `id` (from the `-d<id>.htm` URL) instead of `0`.
  - Availability uses one vocabulary (`in stock`, `limited stock`, `preorder`, `out of stock`, `discontinued`; search cards keep `not purchasable now`) in `get_product`, `compare_products` and `recommend_alternatives`, with the raw text in `availabilityText`. `compare_products` formats prices like `get_product` and has a Brand row.
  - `compare_products` de-duplicates codes case-insensitively, errors when fewer than 2 distinct codes remain and lists ignored duplicates (`duplicatesIgnored`).
  - `get_product_reviews` orders reviews newest first across storefronts (it fetches one 50-review window, orders it, then cuts to `limit`) and notes when the list is longer than the aggregate `reviewCount` (the API appears to also return other storefronts' reviews: Slovak-language reviews were seen live, but it has no market field to confirm this).
  - `find_pickup_points` rejects blank/malformed postal codes (they geocoded to arbitrary lockers), treats `types: []` as "both" (schema now requires at least one), normalises the geocode cache key (`110 00` and `11000` share one request) and the tool description and README disclose the OpenStreetMap Nominatim lookup.
  - `list_categories` sub-level items carry `parentId`. `childCount` stays unset: Alza's pages expose no per-category child counts.
  - `list_category_filters` and `docs/gap-analysis.md` no longer claim all checkbox facets filter: only values with an Alza landing page work (HDMI does; monitor panel type and resolution redirect and error).
  - The `find-product` prompt compares the shortlist with `compare_products` and falls back to `recommend_alternatives` instead of calling `get_product` per candidate.
- Error contract and CLI polish ([#80](https://github.com/lukabudik/alza-mcp-community/issues/80), protocol group):
  - The `report_issue` hint is no longer appended to user mistakes: invalid or expired confirmation tokens, domain validation errors, an unknown postal code, and sign-in problems. HTTP 401 now reads "sign in with `auth_start` → `auth_exchange`" and a 403 on `/api/users/{id}` says `user_id` must equal `profile.user_id` (new `UserError` class). An unknown postal code or a geocoder outage is attributed to the OpenStreetMap Nominatim lookup, not "Alza upstream".
  - Reading `alza://product/{code}` for an unknown product returns the MCP resource-not-found error (-32002) instead of -32603; echoed product codes are truncated. Input-validation errors are one short `path: message` line instead of the SDK's pretty-printed zod JSON (enums are summarised).
  - Upstream HTTP errors no longer embed raw HTML (a Cloudflare challenge page becomes "Cloudflare bot challenge … try another egress or retry later") or the request query string (which carries the visitor id).
  - `upload_attachment`'s `data_url` schema pattern (`^data\:`) was invalid in unicode mode; it is now `^data:`. A test compiles every published schema pattern with the `u` flag.
  - `tools/call` without an `arguments` member now works for tools that take no parameters (`list_toolsets`, `account_status`, ...); the spec makes it optional.
  - HTTP mode: oversized bodies get 413 (was 400), unsupported methods without a session get 405 with `Allow`, and a batched `initialize` says batches are not supported.
  - CLI: `--help`/`-h` and `--version`/`-v` exist; argument and configuration errors print one `alza-mcp: ...` line on stderr (stack only with `ALZA_DEBUG=1`); an unsupported `ALZA_BASE_URL` is rejected before serving and never echoes URL userinfo or query; an empty `ALZA_BASE_URL` counts as unset.
  - Stdio: a malformed JSON-RPC line now gets a `-32700` (parse error) or `-32600` (invalid request) reply with `id: null` instead of silence. Requests before `initialize` are still accepted (MCP SDK default; not changed here).
- `report_issue` redaction ([#64](https://github.com/lukabudik/alza-mcp-community/issues/64)): drafts now also redact `Cookie`/`Set-Cookie` headers and `cf_clearance`-style session cookies, `Authorization: Basic …` and any-case `bearer` tokens, `api_key`/`apikey`/`x-api-key`, `token`/`sid`/`userId`/`invoiceNumber`/`commodityClientId`/`visitor` values, UUIDs, URL userinfo (`https://user:pass@host` keeps the host), `#code=`/long bare `code=` values, quoted values containing spaces, Unicode and `%40`-encoded e-mails, local 9-digit phone numbers, and every URL query value except a small allowlist (`country`, `page`, `scope`, …). Product codes and URL slugs are untouched. The "recent tool errors" section now keeps only the route and status: query strings become `?<query>` and upstream HTML bodies (Cloudflare challenge pages) are dropped.
- The one-time Chromium download no longer writes Playwright's progress to stdout ([#67](https://github.com/lukabudik/alza-mcp-community/issues/67)). On a stdio server (for example a fresh `.mcpb` install, which skips postinstall) those lines landed between JSON-RPC messages; the installer's output now goes to stderr.
- The stdio server now exits (code 0) when the host closes stdin ([#68](https://github.com/lukabudik/alza-mcp-community/issues/68)), closing Chromium and the `curl_cffi` sidecar, instead of running on as an orphan. A sidecar that was still starting when the server shut down is now killed too.
- With `ALZA_CDP_URL`, restarting the attached Chrome no longer breaks every later call until the idle TTL ([#74](https://github.com/lukabudik/alza-mcp-community/issues/74)): the CDP connection now clears its stale browser/context on `disconnected` (or when `isConnected()` is false), and a closed-target error on `newPage` is retried once on a fresh connection.
- `search_products` with a huge `page` (e.g. `99999999999`) froze the whole server for minutes: the sweep loop counted up from 1 to `page` without yielding. `page` is now limited to 1–50, the loop starts at `page`, and `query` (200 chars), `get_product`'s `code` (64) and `find_pickup_points`'s `postal_code` (16) have length limits ([#58](https://github.com/lukabudik/alza-mcp-community/issues/58)).
- alza.sk search results had no price or availability, `max_price` and price sorts did nothing, and `in_stock: true` returned nothing. The card parser now reads `395,90 €` / `297 €` prices and the Slovak CTAs (`Do košíka`, `Vybrať variant`, `Strážiť`); products with an unreadable price are excluded when `min_price`/`max_price` is set instead of always passing ([#70](https://github.com/lukabudik/alza-mcp-community/issues/70)).
- `recommend_alternatives` `same-brand` matched other brands for sized names (`34" iiyama …` for an `AOC` source) because the inch size counted as the brand token ([#71](https://github.com/lukabudik/alza-mcp-community/issues/71)).
- `search_products` with several `producer_ids` returned "No products found (scanned 0 candidates)" because Alza answers combined-brand URLs with a 404. It now accepts one brand id per call and errors clearly otherwise ([#75](https://github.com/lukabudik/alza-mcp-community/issues/75)).
- `search_products` with `producer_ids` on page 1 of a major brand's category (phones + Samsung) failed with "Alza does not support URL filtering" because Alza redirects that page to a curated brand landing page; page 2 worked. The landing redirect is now accepted when it names the requested brand ([#76](https://github.com/lukabudik/alza-mcp-community/issues/76)).
- An unknown `category_id` was silently accepted by `search_products` (unrelated keyword results), `list_category_filters` ("No filters") and `list_categories` ("No categories."). They now return `category N not found` ([#77](https://github.com/lukabudik/alza-mcp-community/issues/77)).
- **`order` and `mobile_read user_order` read real orders again (#60).** Both put the APK's 0/1 `user_flag` into the `/api/users/{userId}/` path segment, which Alza answers with HTTP 403. They now take the numeric `user_id` (from `profile`) and call `GET /api/users/{user_id}/v1/orders/{order_id}?country=CZ[&initialCreated=1]`; `user_flag` is gone and a 0/1 value passed as `user_id` is refused before any request. Coverage row OR1 corrected from `live-verified` to `source-confirmed` (the earlier evidence exercised the anonymous route OR3; the typed fix has not been run live).
- **`complaint_claims`, `subscription_overview`, `address_search` and `claim_detail` are reachable from normal flows (#72).** No tool emitted the `form.meta.href` AppAction they required. `complaint_claims` now takes `user_id` + `scope` (`active`/`archive`, `GET /api/users/{id}/v1/warrantyClaims/{scope}`); `subscription_overview` takes `user_id` (the navigation's `userSubscription` link, `webapi.alza.cz/.../v1/subscription`); `address_search` without an `action` uses the live-verified `getZipCodes` zip/city lookup. `claim_detail`, `complaint_claims` and `subscription_overview` also accept the plain `{href}` links Alza returns, read with GET only and pinned to HTTPS Alza API hosts and to their own route family. The `profile` description no longer promises claim/subscription actions.
- **Large account results no longer flood the text channel (#73).** `order_document` keeps the base64 body in `structuredContent` only and its text reply is metadata (a 350 KB PDF was ~467 K characters of text before, sent twice); `delivery_options` and `payment_methods` get concise id/name/price summaries; every other JSON text reply (`mobile_read`, `claim_detail`, …) is capped at 20,000 characters with a pointer to `structuredContent`, which still carries the full data.
- **Confirmation tokens are now consumed atomically** ([#56](https://github.com/lukabudik/alza-mcp-community/issues/56)). `prepare_mutation` tokens and the `checkout_preview` token were cleared only after the awaited upstream call succeeded, so parallel `tools/call` requests carrying one token all passed the check (three concurrent `pay_after_order` calls sent three payment POSTs). The token is now checked and spent synchronously before the first request; concurrent duplicates fail with `Invalid or expired ... confirmation token`. A failed attempt also spends the token, so a retry needs a fresh `prepare_mutation`. Concurrency regression tests use a counting fetch mock.
- **AppAction tools are bound to their own route family; camelCase sensitive fields are blocked** ([#61](https://github.com/lukabudik/alza-mcp-community/issues/61)). A `review_submit` (or any other AppAction writer) token could drive any same-origin `/api/` route, e.g. the password-change or after-order-payment POST, and the field blocklist needed `_`/`-` delimiters so `oldPassword`, `password1`, `paymentId`, `cardId`, `refreshToken` and `ibanNumber` passed. Every typed AppAction tool now passes a route policy (family keyword + method) that the executor checks on the href and on redirects; credential, payment, order-submission, account-identity and device routes are refused for every tool; sensitive names are matched case-insensitively as substrings. Hrefs with `;` path parameters, encoded slashes, control characters or segments ending in a dot or space are refused, so a keyword cannot be smuggled past the denylist (for example `/afterOrderPayment;address`).
- **Read-only AppAction tools no longer execute GET-shaped writes** ([#62](https://github.com/lukabudik/alza-mcp-community/issues/62)). `claim_detail`, `complaint_claims`, `subscription_overview` and `address_search` passed any same-origin GET through with the bearer token, including `addcoupon`, `delcoupon`, `updBasket`, `unlockbasket`, `addOrderService` and `rateCommodityDiscussionPosts`, which `mutate_list` guards with a token. Readers are now GET-only within their own route family, and those GET writes are refused by the executor for every tool.
- **An empty or non-object 2xx body is no longer reported as an error** ([#63](https://github.com/lukabudik/alza-mcp-community/issues/63)). The account tools passed the raw upstream value as `structuredContent`, so a 204/202 with no body, JSON `null`, an array or text failed the SDK output validation (`Tool pay_after_order has an output schema but no structured content was provided`) after the request had been sent and the token spent, inviting a duplicate payment or delete. Such bodies are now returned as `{accepted: true, data, note}`; the note says the request was accepted and must not be repeated. Object bodies are unchanged.
- Mutations are no longer replayed after an ambiguous sidecar failure ([#57](https://github.com/lukabudik/alza-mcp-community/issues/57)). Before, any sidecar error (including a timeout after the request was sent) re-sent the same POST/PATCH/DELETE over plain fetch and then the browser, so an order step, payment, cancellation or account deletion could reach Alza two or three times. Now only GET/HEAD fall back after such a failure, and other methods fall back only when the sidecar provably never sent them (`TransportUnavailableError`; a sidecar that exits mid-request no longer reports that). Otherwise the tool fails with "may or may not have reached Alza … NOT retried; check the current state first". OAuth token POSTs follow the same rule, and the generic timeout message no longer just says "please retry". The legacy writes that are sent as GET (`addcoupon`, `delcoupon`, `updBasket`, `unlockbasket`, `addOrderService`, `rateCommodityDiscussionPosts`) are treated as writes too.
- An expired stored access token is now refreshed before account reads ([#59](https://github.com/lukabudik/alza-mcp-community/issues/59)). The legacy `restservice.svc` routes behind `profile`, `cart` and `contacts` answer a stale token with HTTP 200 and an anonymous envelope (`user_id: -1`), so the old 401-only refresh never ran and the agent was told the cart was empty. The expiry now comes from the JWT `exp` (or `obtained_at` + `expires_in` in the token store) and the token is refreshed within 60 s of it. An anonymous legacy answer to a loaded token triggers one refresh, after which a read is retried once and a write is reported as an error, never replayed. If the refresh fails, the read fails with an authentication error instead of returning anonymous data. Anonymous catalog reads on the same service (`search`, `category`, `alternatives`, `params`, EAN lookup, `hierarchicalFilter`, discussion posts, delivery countries, zip codes) are exempt: their visitor answer is valid, so they return it as before instead of spending a refresh or failing with a sign-in error. The GET-shaped legacy writes above are never retried after an anonymous answer. `account_status` now reports `expiresAt` and `expired`, and the `add_to_cart` live note is updated.
- Parallel requests that hit a 401 now share one token refresh ([#65](https://github.com/lukabudik/alza-mcp-community/issues/65)). A request whose token was already replaced by another request's refresh retries with the new token instead of redeeming the refresh token again. With one-time refresh tokens, two of three parallel calls used to fail with 401.
- Refreshed tokens are written back to `ALZA_TOKEN_FILE` ([#66](https://github.com/lukabudik/alza-mcp-community/issues/66)), so a restart no longer begins with an expired access token or a spent refresh token. The write is atomic (a 0600 temp file renamed over the store) and keeps the store's other fields. It only happens when the tokens were loaded from that file: never with `ALZA_TOKEN_FILE=none`, never in HTTP mode without `ALZA_HTTP_ALLOW_TOKEN_FILE=1`, and never after an in-process `auth_exchange`. The test suite now runs with `ALZA_TOKEN_FILE=none` by default, so it cannot read or write a developer's real store. Whether Alza rotates refresh tokens is still unresolved (see row A4 in `docs/mobile-endpoint-coverage.md`).
- `after_order_payments` and `order` no longer report an `err:1` envelope as success ([#79](https://github.com/lukabudik/alza-mcp-community/issues/79)). `after_order_payments{order_id: "999999999"}` returned `isError: false` with `"Objednávka se zadaným ID neexistuje"` inside, and a nested `{order: {err: 1, msg}}` left the `order` text as just a heading. Both now fail with `Alza rejected the request (err:1): <msg>` (no bug-report hint); `formatOrder` also shows a nested rejection. `mobile_read` keeps its documented raw-envelope contract.
- `mobile_read` checks each operation's required arguments before sending ([#79](https://github.com/lukabudik/alza-mcp-community/issues/79)). `user_navigation` without `user_id` used to request `/api/users//mainNavigation` (404), `quick_order_summary` without `pgrik`/`ucik` got a 400, and a non-numeric `product_id` went out as `NaN`. These now fail with `Invalid arguments — args.<field>: <operation>: …` and no request. The tool description lists each operation's arguments; `alternatives` takes `commodity_id` (the description said `product_id`, which the code never read).
- Tool annotations match behaviour ([#79](https://github.com/lukabudik/alza-mcp-community/issues/79)): `mutate_list`, `address_upsert`, `change_password`, `two_factor_set`, `phone_change`, `email_change` and `watchdog_delete` now set `destructiveHint: true` (they delete or overwrite data), and `checkout_preview` sets `readOnlyHint: false` (it runs Alza's `sendOrder1` checkout step and replaces the checkout token). The AppAction readers keep `readOnlyHint: true`: since #62 they are GET-only within their own route family.
- An invalid `ALZA_PROXY_URL` now stops the server at startup with a one-line error ([#69](https://github.com/lukabudik/alza-mcp-community/issues/69)). That includes a bad percent-escape, which used to surface as `URI malformed`. The configuration error no longer carries the `report_issue` hint. While a proxy is set, a sidecar failure no longer falls back to an un-proxied plain fetch, which used to bypass the proxy and end in a Cloudflare 403. The managed (proxied) browser is the only fallback, and otherwise the proxy failure is reported. With the sidecar disabled (`ALZA_CF_TRANSPORT=0`), OAuth, AppAction and document requests are refused with a configuration error instead of going out un-proxied.
- The live-canary workflow now installs Chromium and the `curl_cffi` venv explicitly, because `npm ci` in this repository no longer runs those steps.
- `postinstall` now skips both the Chromium download and the `curl_cffi` venv in this repository's own dev install (the documented but unimplemented skip); use `npm run setup:cf` there. `ALZA_MCP_SKIP_INSTALL` and `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD` now skip only the Chromium download, and the new `ALZA_MCP_SKIP_VENV=1` skips only the venv.
- `scripts/ensure-cf-venv.sh` installs `curl_cffi>=0.16,<0.17` (the tested range) instead of an unpinned latest, no longer upgrades pip, and removes a venv it just created when the install fails. A missing `bash` is reported as such in the postinstall log.
- The sidecar interpreter lookup also tries `.venv-cf\Scripts\python.exe`, `python` and `py` on Windows. The README documents what each install path (npx, `--ignore-scripts`, `.mcpb`, dev checkout, Windows) gets.
- `scripts/alza-auth-exchange.mjs` and `scripts/alza_auth_login.py` accept both key styles of `pending-login.json`, so `npm run auth:login:py` followed by `npm run auth:exchange` works.
- Docs: removed stale tool counts and `alza_` prefixes, corrected the read-operation (41) and high-impact (17) counts, replaced the non-standard `n/a` status with `blocked`, updated the roadmap and exclusion lists, and documented `ALZA_CF_TRANSPORT`, `ALZA_CF_PYTHON`, `ALZA_LOG_LEVEL`, `ALZA_OAUTH_CLIENT_ID`, `ALZA_OAUTH_REDIRECT_URI`, `ALZA_COUNTRY` and `ALZA_CULTURE`. `smithery.yaml` and the `.mcpb` manifest text cover `ALZA_PROXY_URL` and the real install behaviour.
- `scripts/alza-auth-smoke.mjs` ships in the npm package (the login script points to it), tool descriptions link to GitHub URLs instead of `docs/` paths the package does not contain, and the ARCHITECTURE.md link to hlidac-shopu uses the `trunk` branch.
- Concurrent first browser calls no longer create one Chromium context each ([#80](https://github.com/lukabudik/alza-mcp-community/issues/80)). Only the last context was tracked, so Cloudflare cookies were split across contexts and, with `ALZA_CDP_URL`, the untracked contexts stayed open in the attached Chrome after shutdown. Context creation is now single-flight, and a context whose creation is overtaken by a shutdown or reconnect is closed instead of tracked.
- The `curl_cffi` sidecar now honours `redirect: "manual"` ([#80](https://github.com/lukabudik/alza-mcp-community/issues/80)). It followed every redirect itself, so the AppAction redirect checks (route allowlist, "mutation redirects are blocked") and the `order_document` redirect refusal never saw a 3xx on the default transport, and a POST body with its bearer token could be replayed to the redirect target. The sidecar protocol has a `followRedirects` field (default `true`); `cfFetch` sets it to `false` for `redirect: "manual"`, and `order_document` refuses a redirect on the sidecar path as it already did on the direct-fetch path.
- The `curl_cffi` sidecar no longer handles one request at a time ([#80](https://github.com/lukabudik/alza-mcp-community/issues/80)). Its docstring said requests were multiplexed, but a synchronous stdin loop made a slow upstream call delay every other request (including other HTTP sessions in catalog mode), and queued requests could hit the Node-side timeout before they were even sent. Requests now run on a bounded pool of 8 worker threads and responses are written whole under a lock, in completion order, matched by `id`.
- `get_product` (and `compare_products` and the PC builder, which use it) no longer drops the inch mark from product names: `27" Philips 27E1N1600AE` came back as `27 Philips 27E1N1600AE`. The name decoder undid the outer `&amp;` of the double-encoded JSON-LD `&amp;quot;` and then deleted every remaining named entity. It now decodes the common ones (`&quot;`, `&apos;`, `&lt;`, `&gt;`, `&nbsp;`, numeric) and drops only unknown ones.
- `profile` and `mobile_read` `user_data` now say "Not signed in" when Alza returns its anonymous account (HTTP 200, `user_id: -1`, null e-mail), which happens without a valid token. Before, this looked like a successful read of the user's account. `scripts/eval.ts`'s `account-read` check accepts that anonymous shape or the older HTTP 403 error, and passes again.

## [0.1.1] — 2026-05-09

### Fixed
- **Memory leak.** The browser used to hold up to 4 pooled pages forever, and one of them ballooned to ~1.9 GB after a few searches because pooled pages accumulate DOM/JS heap across navigations. Pages are now closed after each tool call.
- **Browser never shut down.** Once launched, the headless Chromium ran until the MCP process itself exited — meaning a long-running Claude Code session held a few hundred MB of headless-shell forever. Browser now auto-closes after 3 minutes of tool inactivity (`ALZA_IDLE_TTL_MS` to override). Next tool call relaunches transparently.

Memory profile after the fix: ~215 MB peak during active use, **0 MB** within 3 minutes of the last tool call. Was 4+ GB and growing.

### Added
- `ALZA_IDLE_TTL_MS` env var to tune the idle-shutdown window.
